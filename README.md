# Coach marketplace backend — invite-gated auth scaffold

This is now a full running app: real pages under `app/`, backed by the
API routes below and a Postgres database via Prisma. Buyers self-register,
sellers can only be created by redeeming an admin-issued invite link.


## How the invite gate works

1. You (an ADMIN account) call `POST /api/invites` with a seller's email.
   It creates a random code tied to that exact email, expiring in 7 days.
2. You send the code to the person however you like (email, text, in person).
3. They visit the seller signup form and submit `POST /api/signup/seller`
   with the code, their email, a password, and their profile info.
4. The route checks, server-side: does this code exist, is it still
   `PENDING`, has it not expired, and does the email match? Only if all four
   pass does it create a `SELLER`-role user — inside a database transaction
   that also marks the invite `REDEEMED`, so it can never be used twice.

There is no other code path that creates a seller. A buyer calling the
regular signup endpoint always gets `role: BUYER`, full stop.

```

```

## Payments (Stripe Connect)

This is how buyers pay through the site and sellers get paid out, without
you ever touching a bank transfer yourself:

1. **Seller connects payouts**: `POST /api/stripe/connect` creates a Stripe
   Express account for the seller (first time only) and returns a
   Stripe-hosted onboarding URL. Stripe collects their bank details, tax
   info, and identity verification directly - it never touches your
   database.
2. **Buyer checks out**: `POST /api/checkout` creates a Stripe Checkout
   Session for one gig package and an `Order` row (`PENDING_PAYMENT`). The
   charge goes to *your* Stripe balance, not the seller's - this is what
   makes escrow possible.
3. **Webhook confirms payment**: `POST /api/webhooks/stripe` listens for
   `checkout.session.completed` and flips the order to `IN_ESCROW`. Always
   trust this over the success-page redirect, since a user could hit that
   URL without actually paying.
4. **Release**: once the buyer (or an admin, in a dispute) confirms the
   work is done, `POST /api/orders/[id]/release` calls Stripe's Transfer
   API to send the seller 80% of the price. The 20% platform fee just
   stays in your Stripe balance - no separate step needed. Adjust the cut
   in `lib/stripe.ts` (`PLATFORM_FEE_PERCENT`).

For local testing, use the Stripe CLI to forward webhooks:

```bash
stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

It'll print a `whsec_...` value to put in your `.env`.

## Due dates and messaging during the order

The due date isn't free-standing - it's gated by an actual conversation:

- `/api/checkout` refuses to create an order unless the buyer has sent at
  least one message to the seller AND the seller has replied at least
  once, in their shared `Conversation`. This stops a buyer from locking in
  a deadline before confirming the coach can realistically hit it.
- `/api/conversations/eligibility?sellerId=...` is what the frontend
  calls to decide whether to show the due-date picker as enabled or
  disabled, mirroring the same rule.
- Once an order is `IN_ESCROW`, messaging and video calls both stay fully
  open on that same `Conversation` - nothing in the schema or routes locks
  the thread while work is in progress.


## About your Stripe account and your own payouts

You'll create one Stripe account for the business (linked to your business
bank account). Buyer payments land in that account's Stripe balance, not
your bank account directly:

- **Buyer → your Stripe balance**: automatic on every successful checkout
- **Your Stripe balance → your bank account**: automatic, on whatever
  payout schedule you set in the Stripe dashboard (daily, weekly, or
  monthly) - not something you do by hand each time
- **Your Stripe balance → seller's bank account**: happens only when you
  call the release endpoint, and goes straight to them - their 80% never
  passes through your balance at all

So the only "manual" step in the whole system is deciding, once, how often
you want Stripe to sweep your balance to your bank account. Everything
else - collecting payment, holding it in escrow, splitting the cut, and
paying the seller - is automatic once these routes are wired up.

## Seller invites: one-click email link, not a code to copy

Creating an invite (`POST /api/invites`) now emails the seller directly
via Resend, with a link like:

```
https://yoursite.com/onboard-coach?code=A1B2C3D4&email=seller@example.com
```

They click it, land on a signup form with their email pre-filled, set a
password, and they're in. Nobody has to type or copy a code - the code is
just riding along in the URL. If an email bounces or gets lost,
`POST /api/invites/[id]/resend` sends it again without creating a new
invite.

## Instant messaging (Pusher)

Messages broadcast the moment they're sent - no polling. The pieces:

- `lib/pusher.ts` - server client, plus a helper that names each
  conversation's channel consistently (`private-conversation-{id}`)
- `/api/pusher/auth` - approves a subscription only if the requesting
  user is actually one of the two people in that conversation
- `/api/conversations/[id]/messages` - saves the message, then triggers a
  `new-message` event on that channel so it's delivered instantly
- `lib/hooks/useConversation.ts` - a ready-to-use React hook for the
  frontend: `const { messages, sendMessage } = useConversation(id)`
  loads history once and then keeps the list live

You'll need a free Pusher Channels account for the four `PUSHER_*` env
vars (the `NEXT_PUBLIC_` versions are safe to expose to the browser; the
secret one is not).

## Choosing a Postgres host

**Neon** is the best default here. It's serverless Postgres (scales to
zero when idle, so you're not paying for a database sitting unused),
has a generous free tier, and its "branching" feature lets you spin up a
full copy of your database for testing changes without touching
production - genuinely useful once you're iterating on the schema. One
thing worth knowing: Neon was acquired by Databricks in 2025, which
hasn't changed the product but is worth keeping an eye on if long-term
platform independence matters to you.

**Supabase** is the other strong option, especially if you'd rather not
hand-roll some of what we built ourselves - it bundles Postgres with
built-in auth, file storage, and realtime subscriptions, so you could
potentially replace NextAuth and even Pusher with Supabase's own tools
later. More convenient if you want fewer moving parts; less convenient if
you want to swap pieces out independently.

**Railway** is the simplest choice if you want your database and your
app hosted in the same place with one dashboard - less "best in class"
than Neon or Supabase individually, but very easy to reason about.

For this project, Neon is the right starting point: it's the most
directly compatible with the Prisma-based approach already in this repo.

## Hosting the app itself: alternatives to Vercel

Vercel remains a fine default (it's built by the Next.js team, and
nothing here requires anything Vercel-specific). If you want options:

- **Netlify** - closest direct competitor, similar developer experience,
  slightly less native Next.js support for advanced features.
- **Render** - supports persistent servers, not just serverless
  functions, which matters if you ever want to run something like a raw
  Socket.io server instead of Pusher.
- **Railway** - can host the Next.js app and the Postgres database
  together in one project, which simplifies billing and dashboards if you
  want one place for everything.

None of these require changing the code in this repo - swapping hosts is
a deployment decision, not an application one.

## Setting up "Sign in with Google"

1. Go to https://console.cloud.google.com and create a new project (top-left dropdown → "New Project"). Any name is fine.
2. In the left sidebar, go to **APIs & Services → OAuth consent screen**. Choose "External," fill in the required fields (app name, your email), and save.
3. Go to **APIs & Services → Credentials → Create Credentials → OAuth client ID**.
   - Application type: **Web application**
   - Authorized redirect URI (for local testing): `http://localhost:3000/api/auth/callback/google`
   - Once you're hosting the real site, add a second one: `https://yourdomain.com/api/auth/callback/google`
4. Google will show you a **Client ID** and **Client Secret** - copy both into `.env` as `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.
5. Run `npx prisma migrate dev --name add_google_auth` to add the two new tables Google sign-in needs (`Account` and `Session`).

That's it - the "Continue with Google" button on the login and signup pages will start working.

### Why sellers can never sneak in through Google

Every Google sign-in creates (or logs into) a `User` row through the same
code path, and that row's `role` defaults to `BUYER` unless something
explicitly sets it otherwise. Sellers are only ever created by the
invite-gated `/api/signup/seller` route, which never touches Google
sign-in at all. On top of that, `lib/auth.ts` has an explicit check that
refuses a Google sign-in outright if the email already belongs to a
SELLER or ADMIN account - so even someone who already has a coach account
can't use "Continue with Google" as a side door.

## Reviews, categories, disputes, and everything else in this batch

A lot landed at once - here's the map of what's where.

**Reviews** - a buyer can review an order once it's `RELEASED`, one review
per order (enforced at the database level via a unique constraint on
`orderId`). Shown on the coach's profile page with an average rating.

**Categories & filters** - every gig has a `category` (essay review, mock
interview, application strategy, tutoring, other). `/coaches` has real
filter and sort controls (`components/CoachFilters.tsx`) that rebuild the
URL's query string, so results are shareable/bookmarkable, not just
client-side hidden/shown.

**File attachments** - uses Vercel Blob (`@vercel/blob`) for storage. You
need a free Blob store from your Vercel project's Storage tab, and its
token in `.env` as `BLOB_READ_WRITE_TOKEN`. `/api/upload` handles the
upload itself; `useConversation`'s `sendMessage(body, file)` and the
pre-booking thread on the coach profile page both use it.

**Revision requests & disputes** - both are lightweight flags + a note on
the `Order` row, not a whole workflow engine. A revision request emails
the seller; a dispute emails every admin account. Disputes show up on
`/admin` in a dedicated queue with **Refund buyer** (reverses the actual
Stripe charge) and **Release to coach** (same release path a buyer would
normally trigger) - an admin decides, nothing resolves itself
automatically.

**Scheduled calls** - `/api/orders/[id]/schedule-call` lets either party
lock in a specific date/time for the video call, shown on the order page.
There's no calendar sync (Google Calendar, etc.) - this only tracks the
time within the app itself.

**Discount codes** - created from `/admin`, either percent-off or a fixed
dollar amount. Validated server-side at checkout (never trust a discount
amount the client sends), and the redemption count only increments once
payment actually clears (via the Stripe webhook), not just when someone
types the code in.

**Email notifications** - new message, order paid, payment released,
revision requested, dispute opened, and review received all trigger an
email via Resend, defined in `lib/email.ts`. These are all best-effort -
a failed email logs an error but never blocks the underlying action.

**Terms of Service / Privacy Policy** - `/terms` and `/privacy` are
placeholder legal text, clearly marked as such in the pages themselves.
Get a real lawyer to draft or review these before you launch publicly -
this matters more than usual here given the escrow/payment mechanics.

**Bug fix included in this batch**: the seller dashboard (`/dashboard`)
was fetching *every* seller's gigs instead of just the logged-in seller's
own - fixed via a `?mine=true` param on `/api/gigs` that scopes the query
to the current session.

## New completion flow: seller marks complete, 48-hour auto-release

This replaces the old "buyer clicks release" flow entirely.

**The sequence now:**
1. Order is `IN_ESCROW` (paid, work in progress) - same as before.
2. **The seller** clicks "Mark work as complete" (`/api/orders/[id]/mark-complete`).
   This moves the order to `COMPLETED` and records `workCompletedAt`. The
   buyer gets an email immediately.
3. The buyer now has 48 hours to either:
   - Click **"Release payment now"** - confirms early, releases immediately.
   - Do nothing - the order **auto-releases** once 48 hours pass, no
     matter what.
4. Either way, `releaseOrder()` (in `lib/orderRelease.ts`) is the actual
   code that moves money - it's shared between the authenticated route
   and the cron job so there's exactly one place that logic lives.

**Discount codes removed from checkout.** The field is gone from the
checkout page and the checkout API no longer accepts one. The admin
discount-code creation UI and API are still there (harmless, just
currently has no consumer) in case you want to re-enable it later - see
the note in the admin page.

**Two cron jobs, defined in `vercel.json`:**
- `/api/cron/auto-release` runs hourly - finds every `COMPLETED` order
  where `workCompletedAt` is more than 48 hours ago (and isn't disputed)
  and releases it.
- `/api/cron/overdue-reminders` runs once daily at 9am - finds every
  `IN_ESCROW` order past its due date that hasn't been reminded about in
  the last ~20 hours, and emails the seller.

Both routes check for a `Bearer ${CRON_SECRET}` header - Vercel sends
this automatically for routes listed in `vercel.json`, but **cron jobs
only run once your project is actually deployed to Vercel** - they will
NOT fire while you're just running `npm run dev` locally. To test either
job locally, call it manually with the header set:
```bash
curl -H "Authorization: Bearer your-cron-secret" http://localhost:3000/api/cron/auto-release
```

**Revisions and disputes now work during the 48-hour window too, not
just before.** One important detail: if a buyer requests a revision
while the order is `COMPLETED`, the order resets back to `IN_ESCROW` and
`workCompletedAt` is cleared - this stops the auto-release cron from
paying the seller for work that's mid-revision. Disputes work slightly
differently: the order's status doesn't change, but disputed orders are
excluded from the auto-release query entirely until an admin manually
resolves them (refund or release).

## Revision deadlines

Every revision request (`/api/orders/[id]/request-revision`) automatically
sets the order's due date to exactly 7 days from the moment it's
submitted, overwriting whatever it was before.

If 7 days genuinely isn't enough for a given revision, the seller can
override it with their own date via `/api/orders/[id]/due-date` - this
route is seller-only (a buyer moving their own deadline would defeat the
point of having one), and shows up as a small "Change due date" button
right next to the due date on the order page.

## Dispute conversations

Opening a dispute now creates its own dedicated thread - separate from
the regular buyer/seller conversation - where the buyer, seller, and any
admin can all read and post messages. This is specifically so an admin
can ask follow-up questions before deciding, rather than only seeing the
one-line reason submitted when the dispute was opened.

**Confirming the important part: nothing releases automatically once a
dispute is open.** The auto-release cron explicitly excludes any order
where `disputed: true` (see `/api/cron/auto-release`), regardless of how
much time has passed since the seller marked it complete. The only two
ways money moves after a dispute is opened are an admin calling
`/api/orders/[id]/refund` or `/api/orders/[id]/release` - both require
an active admin session, and both are just buttons on `/admin`.

Pieces involved:
- `DisputeMessage` model - a flat list of messages tied to an order, separate from `Conversation`/`Message`.
- `/api/orders/[id]/dispute-messages` - GET/POST, accessible to the order's buyer, its seller, or any admin.
- `lib/hooks/useDisputeThread.ts` - same real-time pattern as `useConversation`, pointed at a `private-dispute-{orderId}` Pusher channel.
- Opening a dispute automatically seeds the thread with the buyer's original reason as the first message, so there's no gap between "why they disputed" and "the conversation about it."
- Whoever doesn't post gets emailed: admin posts -> buyer and seller are notified; buyer or seller posts -> every admin is notified.
- On `/admin`, each disputed order has a "Respond / get more details" button that expands into the live thread, right above the Refund/Release buttons.
- On the order page itself, the same thread appears automatically (to both buyer and seller) whenever `order.disputed` is true.

## Review window is 96 hours, and the cron runs daily (not hourly)

Two related changes:

**The buyer's review window is now 96 hours** (was 48) - every place that
referenced this (the order page, the mark-complete/release/revision
routes, the emails) has been updated consistently. `AUTO_RELEASE_HOURS`
in `app/orders/[id]/page.tsx` and `WINDOW_HOURS` in
`app/api/cron/auto-release/route.ts` are the two constants that actually
control this - change both together if you ever want a different number.

**The auto-release cron now runs once daily instead of hourly.** This
wasn't optional: Vercel's free Hobby tier only allows cron jobs to run
once per day - an hourly schedule literally fails to deploy on that
tier, it's not just throttled. Rather than requiring a $20/month Vercel
Pro upgrade or a third-party scheduler account just to get slightly
tighter timing, this runs once a day at 3am UTC, which adds at most
~24 hours of slack on top of the 96-hour window - a small fraction of
it, not a meaningful practical delay. If you later upgrade to Vercel
Pro, switching `vercel.json`'s schedule for `/api/cron/auto-release`
back to `"0 * * * *"` (hourly) is the only change needed to tighten it
up - no code changes required.

## Funds-availability check (the "48/96-hour vs. card settlement" fix)

Card payments don't become spendable in your Stripe balance the instant
they're charged - Stripe holds them briefly before they're "available"
to transfer onward. Attempting a Transfer before that point fails.

Rather than guessing a generic "wait 2 business days," this uses
Stripe's own exact number for each specific payment:

1. The moment a payment clears (`checkout.session.completed` webhook),
   the code fetches that charge's `balance_transaction.available_on`
   timestamp - Stripe's own calculation of when *that specific payment*
   becomes available, based on card type, currency, and your account's
   payout schedule. Stored on the order as `fundsAvailableAt`.
2. `releaseOrder()` (in `lib/orderRelease.ts`) checks this before ever
   attempting a Transfer. If funds aren't available yet, it throws a
   specific `FundsNotYetAvailableError` instead of letting Stripe's API
   call fail with a less clear error.
3. **Buyer clicks "Release payment now" too early**: sees a friendly
   message ("still settling, completes automatically around [time]")
   instead of a raw error.
4. **Auto-release cron hits an order too early**: logs it quietly (not
   as an error) and just leaves the order as `COMPLETED` - tomorrow's
   run picks it up again automatically once funds have actually cleared.

If the availability lookup itself fails for some reason (network hiccup,
etc.), `fundsAvailableAt` just stays `null` and the order is treated as
available rather than blocked forever on a missing value - a release
attempt might then occasionally hit Stripe's own error instead, which is
an acceptable fallback for a rare lookup failure.

## Mobile: what's actually true

**This is a website, not a native app.** The backend (`app/api/`) would
be fully reusable by a real iOS/Android app later, but the pages
themselves (`app/coaches/page.tsx` etc.) are built with web technology
and would need to be rebuilt in something like React Native to become a
true App Store/Play Store app. That's a legitimate separate project, not
a small add-on - don't start it until the website itself is proven out.

**What IS done now:**
- **Responsive layout** - the site was already flexible (no fixed
  desktop widths anywhere), and `app/globals.css` now has explicit
  small-screen adjustments (tighter padding, smaller headings) for
  actual phones.
- **"Add to Home Screen"** - `public/manifest.json` plus the
  `manifest`/`themeColor` fields in `app/layout.tsx` let someone add the
  site to their phone's home screen with a proper icon and app-like
  toolbar color, without needing an App Store at all. **One thing you
  still need to do**: `manifest.json` points at `/icon-192.png` and
  `/icon-512.png`, which don't exist yet - drop two actual PNG icon
  files (192x192 and 512x512 pixels) into the `public/` folder with
  those exact names once you have real branding art.
- **Search-result and link-preview basics** - `app/layout.tsx` now has
  proper `openGraph` metadata, so a link to the site shared in a text or
  on social media shows a real title/description card instead of a bare
  URL. Per-page metadata (so `/coaches/[id]` shows that specific coach's
  name in search results, for example) isn't set up yet - that's a
  reasonable next addition once the site's live and you want to optimize
  individual pages for search.

## Stripe Connect now uses the v2 Accounts API

Stripe changed its defaults for new accounts: brand-new Stripe accounts
no longer get access to the older "v1" way of creating connected
(seller) accounts, and - as discovered during testing - the dashboard
toggle meant to re-enable v1 compatibility isn't available on every
account/sandbox. Rather than block on that, `/api/stripe/connect` now
calls Stripe's current v2 Core Accounts API directly via `fetch()`
(rather than the stripe-node SDK's older typed methods, since the
installed SDK version predates v2 support) using a `recipient`
configuration - exactly what a payout-only seller needs: the ability to
receive Transfers from the platform, nothing about accepting their own
separate customer payments.

**Nothing else needed to change.** Once a v2-created account exists, it
works as a normal Transfer `destination` (see `lib/orderRelease.ts`) and
Checkout Sessions (buyer payment) are completely unaffected - Stripe's
account-*creation* restriction didn't touch either of those.

## Testing locally: you need Stripe's CLI to forward webhooks

This isn't new to this update, but worth calling out clearly: an order
only moves from `PENDING_PAYMENT` to `IN_ESCROW` when our server
receives a webhook from Stripe confirming payment - and Stripe's servers
can't reach `localhost` directly. Without forwarding, a test order can
appear to "pay successfully" (Stripe processes the card) while your own
database never gets told about it, leaving the order stuck.

To fix this for local testing:

1. Install the Stripe CLI: `brew install stripe/stripe-cli/stripe` (or see https://docs.stripe.com/stripe-cli for other install methods)
2. Log in: `stripe login` (opens a browser to connect it to your account)
3. In a dedicated Terminal tab, run:
   ```
   stripe listen --forward-to localhost:3000/api/webhooks/stripe
   ```
4. It prints a webhook signing secret starting with `whsec_...` - copy that into `.env` as `STRIPE_WEBHOOK_SECRET`, replacing the placeholder
5. Restart `npm run dev` so it picks up the new env value
6. Keep the `stripe listen` command running in its own tab any time you're testing a real checkout locally

Once deployed to Vercel, this isn't needed anymore - Stripe can reach a
real public URL directly, so this forwarding step is purely a local
development workaround.

## Fixed: Vercel build failures on API routes ("Failed to collect page data")

Real deployment bug: the build script was just `next build`, relying on
Prisma's client code being auto-generated via an install script - the
same kind of script that needed manual approval locally
(`npm approve-scripts`). On Vercel, that generation step can be skipped
silently, leaving every route that imports Prisma unable to actually
query the database the moment Next.js tries to analyze it during build -
which is exactly what "Failed to collect page data" for various API
routes was.

Fixed by making the build script explicit: `"build": "prisma generate && next build"`.
This is the standard, documented fix for deploying Prisma-based apps to
Vercel - never rely on the generation step happening implicitly.

## Fixed: Vercel build failure on /onboard-coach (missing Suspense boundary)

Real production-build error: any page using `useSearchParams()` (this
page reads the invite code and email from the URL) needs to be wrapped
in a `<Suspense>` boundary for Next.js's production build to prerender
it correctly - dev mode doesn't enforce this, so it never showed up
locally. Fixed by splitting the page into a thin wrapper (default
export, wraps everything in `<Suspense>`) and an inner component with
all the actual logic, unchanged.

## Login rate limiting (brute-force protection)

Added after a security review before real student data goes through
this site. Previously, nothing stopped someone from guessing a
password thousands of times in a row.

**How it works**: two new fields on `User` - `failedLoginAttempts` and
`lockedUntil`. Every wrong password increments the counter; after 5
wrong attempts in a row, the account locks for 15 minutes (during which
even a correct password is refused). A successful login resets the
counter to zero.

**Deliberately generic messaging**: a locked-out attempt returns the
same "wrong email or password" response as an actually-wrong password,
rather than a distinct "you're locked out" message - this avoids
confirming to an attacker that a given email address has an account at
all versus just being rate-limited.

This uses your existing database rather than adding a new service
(like Redis) - simpler to operate at this stage, and sufficient for
your current scale. If traffic grows enough that this becomes a
bottleneck, a dedicated rate-limiting service (e.g., Upstash) would be
the next step up - not needed yet.
